# Ferminux Bridge — Red Team Audit (2026-08-20)
Two independent adversarial reviews: contracts and off-chain. No critical findings.

## Review 1

**Verdict:** The bridge's core anti-Nomad/anti-Ronin design is sound: validators recompute transferId and the EIP-712 digest locally (transfer.ts), never trust a submitter's payload (there is no POST route; verifyPayload recovers the signer over a locally-computed digest and rejects malleable sigs), the signature domain binds destination chainId + bridge address, the submitter re-checks processed() on chain and persists nonce+raw-tx before broadcast (proven idempotent by their e2e), and caps are enforced twice. 66/66 unit tests pass. BUT I found a HIGH-severity availability defect that is exploitable against the SAFE default: `staticNetwork` makes ChainClient.healthCheck() a no-op — getNetwork() never dials — so an unreachable/wrong-chain endpoint is never demoted (the wrong-chain alert is dead code), and one dead RPC endpoint permanently stalls a validator under the default requireRpcQuorum=true. I proved this at runtime on ports 8566/8567: the validator logged 'waiting for all endpoints' 49 times and never signed. Because all validators share the same public providers, DDoSing one endpoint halts the whole set (funds locked, none released). A related MEDIUM path turns a DoS of honest endpoints into an unbacked MINT when requireRpcQuorum=false or a single endpoint is configured (config permits one endpoint with zero eclipse detection). Plus a MEDIUM open/unauthenticated, unthrottled HTTP API (ships with empty apiToken) and three lower-severity items. None of these require breaking the contracts. Fix Findings #1 and #2 before mainnet — the eclipse-resistance the whole design rests on is not actually being enforced by the endpoint layer.

### [HIGH] healthCheck() is a no-op: `staticNetwork` makes getNetwork() never dial, so one dead RPC endpoint halts a validator (and the shared-RPC set) under the default requireRpcQuorum=true

**Detail:** In src/chain.ts:57-65 every endpoint's JsonRpcProvider is built with `{ staticNetwork: network }`. In ethers v6 that makes `provider.getNetwork()` resolve locally WITHOUT any JSON-RPC call. But healthCheck() (src/chain.ts:85-124) decides liveness and chain-id correctness solely from `await e.provider.getNetwork()`. Runtime proof: a provider pointed at 127.0.0.1:8599 (nothing listening) returned `getNetwork() -> chainId 3961` (healthy) while `getBlockNumber()` on the same provider threw ECONNREFUSED. Consequences: (1) an unreachable or wrong-chain endpoint is NEVER marked unhealthy, so the whole 'endpoint reports chain id X, expected Y' alert branch (src/chain.ts:91-104) is unreachable dead code — the documented 'every endpoint is probed for the right chain id before it is used' does not happen; (2) because a down endpoint stays in `healthyEndpoints`, confirmSentAcrossEndpoints (src/chain.ts:258-320) counts it as `errored`, and with the DEFAULT requireRpcQuorum=true the transfer is held 'unavailable' (watcher.ts:227-236) forever. I ran a validator on ports 8566/8567 with chain-A endpoints [honest-anvil, dead-8599], requireRpcQuorum=true, sent a real Sent, buried it 5 blocks: the validator logged 'confirmation deferred ... waiting for all endpoints ... ECONNREFUSED' 49 times and NEVER signed. If the dead endpoint is first in the list, even head/scan break because requireEndpoint() (src/chain.ts:126-130) returns healthyEndpoints[0] and getBlockNumber() throws, failing the whole poll. Real-call errors never flip the `.healthy` flag, so this never self-heals.

**Exploit:** The shipped example (config/chains.example.json) gives every chain the SAME two public providers (e.g. publicnode + one vendor), and every validator uses the same list. An attacker DDoSes ONE of those two public RPC providers. Every validator now has that endpoint 'healthy' but erroring; under the default requireRpcQuorum=true each validator refuses to confirm anything ('waiting for all endpoints'). No validator signs -> no 2-of-3 quorum -> the bridge halts on that chain for the duration of the outage, with users' funds already locked on the source side. Taking down a single commonly-used public endpoint is enough. This works against the safe/default configuration.

**Fix:** Do NOT rely on getNetwork() for liveness. In healthCheck() issue a real probe each cycle (e.g. `provider.send('eth_chainId', [])` or getBlockNumber() with a timeout) and set `.healthy=false` on throw or chain-id mismatch — keep staticNetwork for signing/nonce correctness but verify reachability out-of-band. Also flip `.healthy=false` when a data call (getLogs/getBlockNumber) throws, so a persistently dead 'healthy' endpoint is demoted. Then confirmSentAcrossEndpoints will exclude genuinely-dead endpoints and the requireRpcQuorum=true path can proceed on the surviving honest endpoints as the README's 'some endpoints are down; the ones that answered agree' comment already intends.

### [MEDIUM] No enforced minimum of independent RPC endpoints; with requireRpcQuorum=false (or a single configured endpoint) a lone surviving endpoint can mint unbacked tokens

**Detail:** config.ts only rejects a chain with ZERO endpoints (src/config.ts:293); a single rpcUrl is accepted. With one endpoint, checkDivergence() returns early (src/chain.ts:331 `endpoints.length < 2`) and confirmSentAcrossEndpoints() trivially returns 'ok' from that one node (agreed=1, missing=0, errored=0) — the validator's own e2e signs with exactly one endpoint. So a single-endpoint validator has ZERO eclipse/divergence detection yet still signs. Separately, the 'tolerate down endpoints' path (src/chain.ts:308-313) returns 'ok' from the answering endpoints only when requireRpcQuorum=false. Combined with Finding #1 (honest endpoints are trivially knocked offline), an attacker who controls one configured endpoint and DoSes the honest ones gets: agreed=1 (malicious, serving a FABRICATED Sent it hand-crafts so the recomputed transferId matches its topic), errored=N (honest, dead) -> with requireRpcQuorum=false this returns 'ok' and the validator signs a mint for a lock that never happened. The transferId/digest self-checks do not help: they are deterministic and the attacker computes them. The safe default requireRpcQuorum=true prevents the theft (it defers), but leaves the halt of Finding #1.

**Exploit:** Operator runs a validator with requireRpcQuorum=false (a documented footgun) or with a single RPC. Attacker stands up a malicious endpoint in that validator's rpcUrls (or is a malicious RPC vendor already configured), DDoSes the honest endpoint(s), and serves a fabricated `Sent(nonce, srcChainId=Ferminux, dstChainId, token, ..., recipient=attacker, amount=cap)`. The eclipsed validator confirms and signs it. Repeat against a second validator to reach 2-of-3, then relay execute() on the destination: wrapped tokens are minted (or canonical released) with no backing lock on Ferminux — direct insolvency.

**Fix:** Require at least 2 endpoints from distinct hosts for any enabled chain (fail config validation otherwise, matching the README's own guidance). In confirmSentAcrossEndpoints, require a minimum number of AGREEING endpoints (>=2, or >= floor(configured/2)+1) before returning 'ok' — never confirm from a single endpoint when the chain has more than one configured. Consider removing/renaming requireRpcQuorum=false or gating it behind an explicit 'I understand this disables eclipse protection' flag.

### [MEDIUM] Validator/submitter HTTP API has no rate limiting or body-size limit, and ships with authentication OFF (empty apiToken), leaking in-flight transfer details and enabling trivial DoS

**Detail:** src/http.ts applies the bearer check only when `apiToken` is truthy (`if (!this.opts.apiToken) return true` at http.ts:73). Both shipped env templates (deploy/validator.env.example, deploy/submitter.env.example) and the example configs set `FMX_RELAYER_API_TOKEN=`/`apiToken:''`, which parses to an empty string and therefore leaves /metrics, /status, /signatures and /transfers fully open. /transfers returns sender, recipient, amount, route, status and signature counts for every transfer (service.ts:256-273). There is no rate limiting, no max body size, and `closeAllConnections` is the only backpressure. /health is always unauthenticated by design.

**Exploit:** Anyone who can reach the validator's port (the README says validators talk over the public internet in a multi-party deployment, behind only nginx/TLS) reads the full in-flight transfer book without a token if the operator didn't set one — a privacy/operational-intel leak. Separately, unauthenticated /health plus unbounded request handling lets an attacker cheaply exhaust the process's sockets/CPU to keep a validator from serving signatures to the submitter (an availability hit, compounding Finding #1). No direct theft, because execute() delivers only to the sender-chosen recipient.

**Fix:** Refuse to start any role with a network-reachable bind and no apiToken (or force 127.0.0.1-only when unset). Add a simple token-bucket rate limiter and a max request-line/query length. Ship the env templates with a generated token and a comment that an empty token means no auth. Keep /health unauthenticated but make it do zero DB work.

### [LOW] UI advertises Ferminux finality at 12 confirmations while the relayer/economic model requires 64

**Detail:** bridge/ui/src/config.ts:69 defaults Ferminux `confirmations` to 12; the relayer's reasoned value and the shipped chains.example.json use 64 (~7.5 min) precisely because Ferminux is Ethash PoW with no finality gadget. The UI value is advisory only — the contract and relayer are authoritative and the relayer will not attest before its own 64-deep re-read — but useTransfers.ts:112-121 uses the UI's 12 to decide a transfer is 'confirmed' and to start polling the destination, so the UI tells a user their transfer has 'enough confirmations' and is 'executing' roughly six times sooner than any validator will actually sign it, understating reorg risk to the user.

**Exploit:** Not a fund-loss path. A user watching the UI sees 'executing/complete' framing well before economic finality; if they act on that (e.g., treat the source side as settled) during a Ferminux reorg they can be misled. It also produces confusing 'stuck at executing' UX because the destination is polled long before the relayer attests.

**Fix:** Set VITE_CONFIRMATIONS_FERMINUX default to 64 to match the relayer's reorg budget, and source the UI confirmation counts from the same table the relayer uses so they cannot drift.

### [LOW] Keystore password accepted from FMX_RELAYER_PASSWORD env with no protection, unlike the file path which enforces 0400

**Detail:** readPassword() (src/keystore.ts:36-51) enforces mode & 0o077 on a password FILE but accepts `FMX_RELAYER_PASSWORD` from the environment with no checks; the keygen path (src/index.ts:194) likewise reads the password file without the mode check the loader applies. Environment variables are readable via /proc/<pid>/environ by the same user, can appear in crash/core dumps, in `ps e`, and are inherited by child processes. The logger redacts the key `password` (logger.ts:20) so it won't be logged, and the file path is the documented preferred method, but nothing stops an operator from using the env var for the signing-key password.

**Exploit:** A local user, a core dump shipped to a crash aggregator, or a child process spawned by the relayer host can read the keystore password out of the environment; combined with read access to the keystore file it yields the validator signing key.

**Fix:** Warn loudly (or refuse in production/NODE_ENV=production) when the keystore password comes from FMX_RELAYER_PASSWORD instead of a 0400 file, and apply the same mode check in the keygen password-file read.

### [INFO] Local 24h volume capacity is consumed before signing but not released on the post-consumption reject paths

**Detail:** verifyForSigning() durably consumes the rolling-window capacity (limits.ts tryConsume) as its last step before returning ok (verify.ts:201-224). If signing then fails on the two defensive reject paths in validator.ts — self-check signature-recovery mismatch (validator.ts:126-136) or 'digest changed between verification and signing' (validator.ts:138-141) — the transfer is marked 'rejected' but the consumed outbound/inbound capacity is never released. Same for an exception thrown between consumption and status update, which leaves the transfer 'confirmed' and re-consumes on the next tick.

**Exploit:** Not attacker-exploitable and not a fund-loss path: the only effect is the validator under-counts its own remaining 24h capacity and becomes MORE restrictive (fails safe), potentially refusing later legitimate transfers until the window drains.

**Fix:** Release consumed capacity (limiter.release on both windowKeys) in the self-check-failed and digest-changed branches, and wrap consume+sign so any throw after consumption releases before rethrowing.

## Review 2

**Verdict:** Red-teamed FerminuxBridge.sol and BridgeToken.sol with 36 Foundry PoCs in <scratch>/bridge-attack (all passing; repo untouched, its own 250 tests still green). 11 findings: 1 high, 5 medium, 4 low, 1 info. No critical — I found no path for an unprivileged attacker to steal funds.

The high is a genuine missed check: `_safeTransfer`/`_safeTransferFrom` (FerminuxBridge.sol:846-855) never verify the callee has code, so a raw `.call` to a dark token returns success. In `execute()`'s canonical-release branch that lands AFTER `processed[transferId] = true` and `lockedBalance -= amount`, so the transfer is marked delivered, the collateral is written down, and nothing moves — final and unretryable, unlike every other failure mode here, which reverts. Reachable via SELFDESTRUCT on Ferminux itself (geth 1.10.26 fork = pre-Cancun, EIP-6780 not in effect) and, chain-agnostically, via any canonical token behind a proxy whose implementation is zeroed. The tell that it was missed rather than accepted: `send()` fails safe against the identical token purely by accident, because `balanceOf()` carries the compiler's extcodesize guard.

The mediums are mostly invariant breaks around the collateral/surplus boundary. `execute()` with `recipient == address(this)` (no guard at line 490) turns locked collateral into `rescue()`-able surplus, falsifying the NatSpec at line 591, security-model §4, and `test_Rescue_CannotTouchLockedCollateral` — and silently destroys the user's funds with an `Executed` event indistinguishable from a real delivery. `withdrawFees` is the only value-moving path with neither a solvency guard nor a pause check, so it pays the collector out of principal once the bridge is short. Migration bricks every wrapped holder: `BridgeToken.bridge` is immutable and `registerWrapped` demands `bridge() == address(this)`, so the documented "pause() and migrate" response leaves wrapped supply with no exit but the contract you migrated away from. `transferOwnership` is the one privileged change outside the timelock — contradicting the contract's own line-45 claim — and `pendingOwner` can never be cleared or expire. And `registerWrapped`'s "not the minter" guard, which the docs cite as blocking uncontrolled wrappers, is spoofable by any 30-line proxy.

Worth saying plainly: the signature path held up under everything I threw at it — duplicate signers, malleable twins, bad `v`, `ecrecover` returning zero, cross-chain and cross-deployment domain reuse, rotation and threshold changes mid-flight. Replay protection is checks-effects-interactions correct. Reentrancy is properly guarded including cross-function. The balance-delta metering in `send()` is sound — I tried fee-on-transfer, reflection/redistributing tokens and an ERC777-style hook that donates mid-`transferFrom`, and could not construct a version where the sender was credited more than they parted with. `lockedBalance` underflow is a real hard ceiling. The timelock is not an arbitrary-call machine and I could not smuggle calldata past the selector whitelist. The 2× cap burst the docs claim is exactly right — I measured 200.0% with 7-second top-ups — and PoW timestamp skew is not a lever (15s moves the bucket 0.017%). A 256-run solvency fuzz found no violation. The docs are unusually honest, and several things I initially took for findings turned out to be disclosed there already; those I've either dropped or reported at the level the disclosure gap actually warrants.

### [HIGH] _safeTransfer has no existence check: execute() release against a code-less token is a silent no-op that still consumes the transferId and writes down the collateral

**Detail:** FerminuxBridge.sol:846-855. `_safeTransfer`/`_safeTransferFrom` accept `ok && (ret.length == 0 || abi.decode(ret,(bool)))` — the empty-return branch is needed for USDT-shaped tokens, but there is no `token.code.length > 0` check, which is exactly what OpenZeppelin's SafeERC20 adds via `functionCall`. A raw `.call` to an address with no code returns `ok = true` with empty returndata, so the require passes.

The consequence is confined to `execute()`'s canonical-release branch (FerminuxBridge.sol:510-518), and it is the worst possible one, because `execute()` is checks-effects-interactions correct: `processed[transferId] = true` (line 508) and `lockedBalance[t.dstToken] -= t.amount` (line 513) are already committed when `_safeTransfer` returns its fake success. The transfer is marked delivered, the collateral is written down, `Executed` is emitted, and nothing moved. Unlike every other failure mode in this contract — `BRIDGE: native transfer failed`, `BRIDGE: transfer failed`, cap rejections, pause — which all revert and are therefore retryable, this one is final and unrecoverable.

The asymmetry is the tell that it was missed rather than considered: `send()` fails safe against the identical token (test_C1b) purely by accident, because it reads `balanceOf()` at line 423, and Solidity does insert an extcodesize guard for calls that expect return data. I verified the same guard also protects the `IBridgeToken.burn` path (test_Probe_VoidReturnCallToCodelessWrapperFailsSafe). `_safeTransfer` is the one door left open, because a raw `.call` bypasses the compiler's guard entirely.

Reachability is not hypothetical on this chain. ferminux-geth is a fork of geth v1.10.26 — London/Paris, pre-Cancun — so EIP-6780 is not in effect and SELFDESTRUCT still clears code on chain 3961 for contracts deployed in any earlier transaction. A canonical token that retains a selfdestruct, or a metamorphic CREATE2 token, removes its own code at will. And the chain-agnostic variant needs no SELFDESTRUCT at all: any canonical token behind a proxy whose implementation is zeroed or destroyed keeps its own code but delegatecalls into nothing, which returns success with empty returndata — the same fake success, on Ethereum and BSC as much as on Ferminux (test_C8). docs/security-model.md §7 tells operators not to register malicious or upgradeable tokens, but says nothing about a token merely going dark, and frames the failure mode for a broken canonical token as reverting releases and frozen collateral, not as silent delivery.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack3.t.sol::test_C1_ReleaseAgainstACodelessTokenSilentlySucceeds and test/Attack4.t.sol::test_C8_CanonicalReleaseThroughADeadProxyIsASilentNoop — both PASS.

1. usdx is registered CANONICAL. alice sends 100 USDX; lockedBalance = 99.9e18.
2. The token loses its executable code — `vm.etch(usdx, "")` in C1 (models SELFDESTRUCT on pre-Cancun Ferminux); in C8 the token is replaced by a proxy whose implementation slot is zeroed, which is Cancun-proof and needs no SELFDESTRUCT.
3. A relayer submits a genuine 2-of-3-signed inbound transfer for 50 USDX to bob. `execute()` does NOT revert.
4. Asserted after the call: `processed[transferId] == true`, `lockedBalance` fell by exactly 50e18, `usdx.code.length == 0`, and bob's balance is unchanged. The transferId is burned, so the transfer can never be re-relayed even after the token's code is restored — a temporary token outage has been converted into a permanent bridge loss. Repeat for every in-flight transfer on that route to write the entire collateral pool down to zero while paying nobody.

**Fix:** Add an existence check to both helpers in FerminuxBridge.sol:846-855, mirroring SafeERC20:

```solidity
function _safeTransfer(address token, address to, uint256 amount) internal {
    require(token.code.length > 0, "BRIDGE: token has no code");
    (bool ok, bytes memory ret) = token.call(abi.encodeWithSelector(IERC20Minimal.transfer.selector, to, amount));
    require(ok && (ret.length == 0 || abi.decode(ret, (bool))), "BRIDGE: transfer failed");
}
```

and identically in `_safeTransferFrom`. This makes the dark-token case revert, which is the correct behaviour: the transfer stays unprocessed and is retried once the token is healthy. Belt-and-braces for the dead-proxy variant, which passes a code check: assert the release actually moved value, by bracketing the transfer in `execute()` with a balance read the way `send()` already does — `uint256 before = IERC20Minimal(t.dstToken).balanceOf(address(this)); _safeTransfer(...); require(before - IERC20Minimal(t.dstToken).balanceOf(address(this)) >= t.amount, "BRIDGE: release did not settle");` — noting this deliberately makes fee-on-transfer releases revert, so gate it on a per-token flag if FoT routes are to stay supported.

### [MEDIUM] execute() to the bridge's own address converts locked collateral into rescue()-able surplus, breaking the documented rescue guarantee and destroying user funds finally

**Detail:** FerminuxBridge.sol:510-521 never checks `t.recipient != address(this)`. `t.recipient` is a free field chosen by whoever called `send()` on the source chain; nothing privileged is required to put the destination bridge's own address there.

On the CANONICAL branch the release becomes a self-transfer. `_safeTransfer(token, address(this), amount)` is a real ERC20 transfer from the bridge to the bridge: it succeeds and leaves the balance sheet untouched. For native, `_safeTransferNative(address(this), amount)` calls the bridge with value, lands in `receive()` (line 291), emits `NativeReceived` and succeeds — again with no net balance change. But line 513 has already run `lockedBalance[t.dstToken] -= t.amount`. Balance stayed flat while the reserved amount fell, so `surplusOf()` (line 386, `balance - lockedBalance - accruedFees`) now reports exactly the destroyed amount as surplus.

That directly contradicts what the code and docs promise. The `rescue()` NatSpec at line 591 says it moves 'tokens the bridge holds but does not owe — airdrops, dust, mistaken direct transfers. Cannot touch lockedBalance'; docs/security-model.md §4 lists `rescue` as 'capped at surplusOf... Airdrops and dust only; BRIDGE: exceeds surplus protects collateral'; and test_Rescue_CannotTouchLockedCollateral asserts it. All three are true only as long as nobody exercises this path. The collateral involved is pooled — it is the backing for other users' outstanding wrapped IOUs — and the owner multisig can now walk out with it through the one owner power that has no timelock and no pause check.

The WRAPPED branch (line 520) is the same shape from the other end: `mint(address(this), amount)` credits the bridge freshly minted IOUs against remote collateral, and since `lockedBalance` for a wrapped asset is always zero, the whole minted amount reads as surplus and is immediately rescuable.

Even with a scrupulously honest owner this is a fund-loss bug rather than a bookkeeping curiosity. `processed[transferId] = true` is set at line 508 before the transfer, so the value is destroyed permanently and the transfer can never be retried. docs/security-model.md §10.7 disclaims 'user error — a wrong recipient is signed into the transfer and is final', but §8 sets the expectation that a bad recipient produces `BRIDGE: native transfer failed` 'forever for that transfer' — i.e. a revert that leaves the transfer recoverable by a discretionary quorum-signed compensating transfer. This one is silent success: `Executed` fires, monitoring sees a clean delivery, and there is no event that distinguishes it from a real one.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack.t.sol::test_A1_ExecuteToBridgeTurnsCollateralIntoRescuableSurplus_ERC20, test_A1b (native), test_A1c (wrapped mint), test_A1d (silent finality) — all four PASS.

ERC20 case, asserted end to end:
1. alice sends 100 USDX. Pre-state: balance == lockedBalance + accruedFees, `surplusOf(usdx) == 0`.
2. A relayer executes a normally-signed 2-of-3 inbound transfer for 60 USDX with `recipient = address(bridge)`.
3. `usdx.balanceOf(bridge)` is unchanged; `lockedBalance` dropped by 60e18; `surplusOf(usdx)` is now 60e18.
4. `vm.prank(owner); bridge.rescue(usdx, owner, 60 ether)` succeeds — the owner holds 60 USDX of live user collateral, via the function documented as reaching only airdrops and dust.

Native (A1b): identical, 50 FMX of locked collateral becomes surplus and is rescued. Wrapped (A1c): 40e18 of freshly minted wRMT lands as surplus and is rescued with no source-chain deposit backing the owner's claim.

**Fix:** One line in `execute()`, alongside the existing zero-recipient guard at FerminuxBridge.sol:490:

```solidity
require(t.recipient != address(0), "BRIDGE: zero recipient");
require(t.recipient != address(this), "BRIDGE: recipient is the bridge");
```

Add the mirror guard in `send()` after line 407 so the bad recipient is rejected at origin, where the user still has their money, rather than at destination where it is already unrecoverable — note the check must be against the REMOTE bridge address, so either store it per route in TokenConfig or, if the deployments are address-identical across chains as the deterministic-deploy scheme intends, reject `recipient == address(this)` there too. Also add a regression test asserting `surplusOf()` is unchanged across any `execute()`, since that is the invariant this violates.

### [MEDIUM] withdrawFees() has no solvency check and pays the fee collector out of user collateral when the bridge is under-collateralised

**Detail:** FerminuxBridge.sol:576-588. `withdrawFees` reads `accruedFees[token]`, zeroes it, and transfers that amount out. It never compares the bridge's actual holdings against `lockedBalance[token]`.

The contract is careful about this everywhere else. `rescue()` at line 597 gates on `surplusOf(token)`, which subtracts both `lockedBalance` and `accruedFees`, so it correctly refuses to move anything once the bridge is short. `execute()` at line 513 relies on `lockedBalance -= t.amount` underflowing as a hard collateral ceiling, which docs/security-model.md §3 leans on explicitly — 'They cannot take more than the bridge ever held.' `withdrawFees` is the one value-moving path with neither guard, and it is also — with `rescue` — one of only two that skip the pause check (test_Pause_DoesNotBlockFeeWithdrawalOrRescue asserts this is intentional), so it remains live during exactly the incident where the shortfall appears.

`accruedFees` and `lockedBalance` are independent counters, so once `balance < lockedBalance + accruedFees` the fee sweep is drawn from whatever is actually there — which is collateral. The invariant the whole design rests on, 'lockedBalance is collateral the bridge OWES to inbound transfers, never rescuable' (line 143), silently stops holding.

The shortfall is reachable through several routes the docs already acknowledge as live risks: a stablecoin issuer clawback or blacklist-with-burn on a canonical route (§7 flags USDT/USDC blacklisting but only predicts reverting releases, not a fee sweep eating principal); a canonical token that rebases down; a broken or malicious registered token; or the recipient-is-the-bridge path in the preceding finding. My 256-run solvency fuzz (test_B8) found no way to reach it with a well-behaved ERC20, so this is strictly a second-line defence — which is exactly what `rescue()` already has and `withdrawFees` does not.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack.t.sol::test_A7_WithdrawFeesDipsIntoCollateralWhenBalanceShrinks — PASSES.

1. A canonical token with an issuer clawback (`SeizableToken`) is registered. alice sends 100; the bridge holds lockedBalance 99.9 + accruedFees 0.1 = exactly its balance.
2. The issuer confiscates 50 from the bridge address. Asserted: `balanceOf(bridge) < lockedBalance + accruedFees` — the bridge is insolvent.
3. `surplusOf()` returns 0 and `rescue()` correctly refuses. The guard works.
4. `vm.prank(collector); bridge.withdrawFees(sz)` succeeds anyway. The collector receives the full 0.1 fee, paid out of the remaining collateral, and the assertion `balanceOf(bridge) < lockedBalance` then holds — the shortfall owed to inbound transfers is now strictly larger than it was before the sweep.

**Fix:** Cap the sweep at what is genuinely unreserved, in FerminuxBridge.sol:576:

```solidity
function withdrawFees(address token) external nonReentrant {
    require(msg.sender == owner || msg.sender == feeCollector, "BRIDGE: not fee authority");
    uint256 amount = accruedFees[token];
    require(amount > 0, "BRIDGE: no fees");
    uint256 bal = token == address(0) ? address(this).balance : IERC20Minimal(token).balanceOf(address(this));
    require(bal >= lockedBalance[token] + amount, "BRIDGE: would impair collateral");
    accruedFees[token] = 0;
    ...
}
```

That makes the fee sweep fail closed under exactly the conditions `rescue()` already fails closed under, and turns a silent impairment into a loud alert. Add the same regression assertion — `balance >= lockedBalance` after any fee withdrawal — to BridgeAccounting.t.sol.

### [MEDIUM] A bridge migration permanently strands every wrapped holder: BridgeToken.bridge is immutable and registerWrapped's minter check makes adoption by a v2 impossible

**Detail:** BridgeToken.sol:40 declares `address public immutable bridge`, set once in the constructor with no rotation path, and `mint`/`burn` are `onlyBridge` (lines 50-53, 92, 106). FerminuxBridge.sol:754 requires `IBridgeToken(localToken).bridge() == address(this)` before a wrapper can be registered. Together these make outstanding wrapped supply un-migratable by construction: a redeployed bridge can never register the existing wrappers, and therefore can never burn them, so holders have no exit that does not run through the contract that was abandoned.

This matters because migration is the documented incident response, not an exotic scenario. docs/security-model.md §6 states 'No upgrade path | deliberate... The response to a contract bug is pause() and migrate', and the migration row directly beneath it discusses only the canonical side: 'collateral is lockedBalance and rescue() cannot touch it. Migrating a bridge that holds collateral means draining it by user action (everyone bridges home) or discretionary quorum-signed compensating transfers.' Neither sentence is available to a wrapped holder. There is no user-callable burn on BridgeToken, no redemption function, and no way for the new bridge to honour the IOU.

So the stated playbook is internally inconsistent: `pause()` is the correct first move and is instant, but every second the v1 bridge stays paused is a second in which the entire wrapped supply on that chain is frozen with no alternative venue. The only way to let wrapped holders out is to unpause the very contract you migrated away from because you no longer trust it, and then race the attacker to the exit — which is the situation pausing was supposed to end. `rescue()` cannot help, `execute()` on v2 reverts with `BRIDGE: token not registered`, and there is no compensating-transfer path because v2 has no registration for the asset.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack2.t.sol::test_B1_RedeployedBridgeCannotAdoptExistingWrappedSupply — PASSES.

1. Real wrapped supply is created honestly: a signed inbound transfer mints 100 wRMT to bob. `wrmt.totalSupply() == 100e18`.
2. Incident response per the docs: `vm.prank(pauser); bridge.pause()`, then deploy v2 with identical bytecode, owner, validator set and pauser.
3. The owner queues `registerWrapped(wrmt, ...)` on v2 and waits the full 48 h timelock. `executeAction` reverts with `BRIDGE: not the minter` — asserted. v2 can never adopt the wrapper.
4. bob has no exit: `bridge.send(wrmt, ...)` reverts `BRIDGE: paused`; `v2.send(wrmt, ...)` reverts `BRIDGE: token not registered`. Final assertion: bob still holds 100 wRMT, permanently unredeemable, while the collateral backing it sits locked on the origin chain.

**Fix:** Give BridgeToken a bridge-rotation path that is at least as slow and as observable as the rest of governance. Minimal version: replace the immutable with `address public bridge; address public pendingBridge; uint64 public bridgeEta;`, add `proposeBridge(address)` and `acceptBridge()` callable only by the CURRENT bridge and separated by a delay no shorter than FerminuxBridge.MIN_TIMELOCK_DELAY, and expose `FerminuxBridge.proposeWrapperBridge(address token, address newBridge)` as a tenth `onlySelf` selector in `_isTimelocked` (line 720) so the handover inherits the 48 h notice and the ActionQueued alert. `registerWrapped`'s minter check then keeps working unchanged for v2 after the handover completes.

If immutability is genuinely preferred over migrability — a defensible call, since a rotatable minter is a new attack surface — then say so explicitly in docs/security-model.md §6 and add the operational consequence to the migration row: a migration cannot pause v1 until wrapped supply has been drained to zero, which means the drain must happen while the known-bad contract is still live. Also add it to §10 as an eleventh thing the design does not protect against.

### [MEDIUM] transferOwnership sits outside the timelock and pendingOwner can never be revoked or expire, leaving an abandoned handover as a permanent takeover key

**Detail:** Two related gaps in FerminuxBridge.sol:660-671.

First, ownership is the only privileged change that skips the timelock. `_isTimelocked` (line 720-726) whitelists nine selectors and `transferOwnership` is not among them, so the handover is a plain `onlyOwner` call plus `acceptOwnership()` — no `ActionQueued` event, no 48 h, no cancellation window. That contradicts the contract's own NatSpec at line 45, which states the safety model as '48h timelock on everything that could ENLARGE the blast radius', and the ownership seat is the largest blast radius in the system: docs/security-model.md §1 ranks it above the validator set, and §4 concludes 'the owner multisig is the single point of total failure.' The doc does list it under instant powers ('transferOwnership(attacker) | needs acceptOwnership() from the attacker; two-step, no delay'), so this is disclosed rather than hidden — but disclosed inconsistently with the contract's stated principle, and it means the single highest-value monitoring alert in the system, ActionQueued, never fires for the single highest-value change. A new owner holds every instant power the moment they accept: `rescue`, `withdrawFees`, `setPauser`, `pause`, `unpause`, `decreaseTokenLimits`, and the ability to cancel any action the legitimate owner had queued.

Second, and undisclosed anywhere: `pendingOwner` is write-only-forward. `transferOwnership` requires `newOwner != address(0)` (line 661), so there is no way to clear a pending handover, and `acceptOwnership` has no deadline — the offer stays live forever. A handover that is proposed and then abandoned (wrong address, a multisig that was never stood up, a candidate whose keys were generated on a machine that was later compromised) leaves a standing, silent takeover key with no on-chain expiry and no revocation. The only workaround is the non-obvious `transferOwnership(currentOwner)` followed by `acceptOwnership()` from the current owner, which is nowhere in docs/operations.md.

**Exploit:** PoCs at <scratch>/bridge-attack: test/Attack.t.sol::test_A5_OwnershipHandoverBypassesTheTimelockEntirely and test/Attack2.t.sol::test_B2_PendingOwnerIsAnUnrevokableStandingTakeoverKey — both PASS.

A5: `bridge.queue(abi.encodeCall(transferOwnership, attacker))` reverts `BRIDGE: selector not timelockable` — asserted — because it does not need the timelock. The direct call plus `acceptOwnership()` moves ownership in one block with no ActionQueued emitted. The new owner then immediately runs `decreaseTokenLimits(usdx, 0, 0)` (freezing the route for 48 h, since only the timelocked `setTokenLimits` can restore it), `setPauser(attacker, true)` and `pause()` — all asserted to succeed.

B2: the owner calls `transferOwnership(candidate)`, then tries to cancel with `transferOwnership(address(0))` — reverts `BRIDGE: zero owner`, asserted, and `pendingOwner` is still the candidate. `vm.warp(block.timestamp + 730 days)`, then `vm.prank(candidate); bridge.acceptOwnership()` succeeds. Ownership transfers two years after the handover was abandoned, from a key nobody was still guarding.

**Fix:** Bring the handover under the machinery that already exists. Add `this.transferOwnership.selector` to `_isTimelocked` at FerminuxBridge.sol:720 and change the function to `onlySelf`, so proposing a new owner emits `ActionQueued` and serves the full delay before `pendingOwner` is even set; `acceptOwnership` stays a plain second step by the incoming owner. `cancelAction` then gives a real revocation path for free.

For the stale-offer half, add an expiry and an explicit cancel:

```solidity
uint64 public pendingOwnerExpiry;
function cancelOwnershipTransfer() external onlyOwner { pendingOwner = address(0); emit OwnershipTransferStarted(address(0)); }
function acceptOwnership() external {
    require(msg.sender == pendingOwner, "BRIDGE: not pending owner");
    require(block.timestamp <= pendingOwnerExpiry, "BRIDGE: offer expired");
    ...
}
```

with `pendingOwnerExpiry = uint64(block.timestamp) + GRACE_PERIOD` set on proposal — the same 14-day staleness rule already applied to queued actions, for consistency. Add a monitoring line to docs/operations.md §6 for `OwnershipTransferStarted`, which today is emitted but is not on the alert list.

### [MEDIUM] No success or supply-delta check on IBridgeToken.mint/burn, and registerWrapped's 'not the minter' guard is trivially spoofable

**Detail:** FerminuxBridge.sol:448-449 and 520 call `IBridgeToken(localToken).burn(...)` and `.mint(...)` and check nothing. Both return void, so there is no return value to inspect, and the contract makes no attempt to confirm that supply actually moved. I confirmed solc 0.8.24 does still emit an extcodesize guard for these zero-return-size calls, so a fully code-less wrapper fails safe (recorded in test/Probe.t.sol) — the exposure is a wrapper that HAS code and returns success without acting.

The guard that is supposed to prevent that is FerminuxBridge.sol:754, `require(IBridgeToken(localToken).bridge() == address(this), "BRIDGE: not the minter")`. docs/security-model.md §7 presents it as a closed door: 'Wrapper not controlled by the bridge | would make inbound unfillable | already blocked: registerWrapped requires bridge() == address(this)'. But it proves only that one view function returns the right address at registration time. Any contract can return anything from `bridge()`, and a proxy can pass the check on Monday and behave differently on Tuesday. My `ProxyWrapper` — 30 lines, a mutable `impl` slot, a hardcoded `bridge()` — passed registration through the full 48 h timelock without complaint.

The consequence is worse on the outbound leg than a stuck transfer. In `send()` the burn at line 448 is the entire basis for the `Sent` event emitted at line 466: if `burn` silently no-ops, the bridge still books the fee, still emits a fully-formed `Sent(net)`, and validators watching the event chain sign it in good faith. The canonical side then releases real collateral against a burn that never happened. The wrapped supply is not destroyed, so the same tokens can be sent again. The docs bound the damage from a bad token to 'that token's route', which is technically true but understates it: the loss lands on the OTHER chain's locked collateral pool, i.e. other users' principal, not on holders of the bad wrapper.

On the inbound leg (line 520) the mirror failure marks a transfer delivered and consumes the cap while minting nothing — and because `processed[transferId] = true` was set at line 508, it is final, not retryable.

This is a governance-error class, not an unprivileged attack: in normal operation the owner deploys the shipped immutable `BridgeToken`, which has no such hole. But nothing in the code enforces that, the one check that looks like it does is cosmetic, and the docs cite it as protection.

**Exploit:** PoCs at <scratch>/bridge-attack/test/Attack4.t.sol::test_C6_WrappedBurnSilentlySucceedsAgainstACodelessToken and ::test_C7_WrappedMintSilentlySucceedsAndBurnsTheTransferId — both PASS.

C6, outbound: a `ProxyWrapper` with a working implementation passes `registerWrapped` through the full timelock. alice is given 100 wrapped tokens the honest way, via a signed inbound transfer. The implementation is then set to address(0) — the proxy still has code, so the compiler's extcodesize guard does not fire, and its delegatecall into nothing returns success with empty returndata. `bridge.send(w, 100 ether, ...)` succeeds and returns a non-zero transferId, so a valid `Sent` for 99.9e18 is emitted. Restoring the implementation shows alice's 100e18 balance untouched — asserted — while the canonical chain has already been told to release. The bridge even booked `accruedFees == _fee(100 ether)` on the phantom burn.

C7, inbound: same wrapper with a dead implementation. A 2-of-3-signed transfer for 100e18 to bob executes without reverting; `processed[transferId] == true` is asserted, and after restoring the implementation bob's balance is asserted to be 0. Permanently.

**Fix:** Two changes in FerminuxBridge.sol.

First, verify the effect rather than the call. Wrap both call sites in a supply assertion, which is cheap because BridgeToken already exposes `totalSupply`:

```solidity
// send(), wrapped branch
uint256 supplyBefore = IERC20Supply(localToken).totalSupply();
IBridgeToken(localToken).burn(msg.sender, received);
if (fee > 0) IBridgeToken(localToken).mint(address(this), fee);
require(supplyBefore - IERC20Supply(localToken).totalSupply() == received - fee, "BRIDGE: burn did not settle");

// execute(), wrapped branch
uint256 balBefore = IERC20Minimal(t.dstToken).balanceOf(t.recipient);
IBridgeToken(t.dstToken).mint(t.recipient, t.amount);
require(IERC20Minimal(t.dstToken).balanceOf(t.recipient) - balBefore == t.amount, "BRIDGE: mint did not settle");
```

Both reads carry the compiler's extcodesize guard, so they also close the code-less case for this path. Second, stop claiming `bridge()` is a control: either harden `registerWrapped` at line 754 by additionally requiring the candidate's runtime code hash to equal a `BRIDGE_TOKEN_CODEHASH` immutable set at deploy time (which pins registrations to the audited BridgeToken bytecode and rejects every proxy), or amend the docs/security-model.md §7 row to say plainly that the check is an anti-typo measure and that registering any wrapper other than the shipped BridgeToken puts the counterpart chain's collateral at that wrapper author's discretion.

### [LOW] Registry does not enforce that a remote (chainId, token) pair is claimed by at most one local token

**Detail:** FerminuxBridge.sol:758-782. `_register` checks that the LOCAL token is unregistered (line 767), that the remote chain is non-zero and not this chain, and that the caps are sane. It never checks whether some other local token already points at the same `(remoteChainId, remoteToken)`.

So one remote asset can be mirrored by two different local assets simultaneously — one CANONICAL and one WRAPPED, or two WRAPPED — each with its own `lockedBalance`, its own caps, its own volume buckets and its own transferId space. On the inbound side both registrations pass every check in `execute()` (lines 496-500) for the same source deposit, because the registry lookup is keyed on `t.dstToken` and the only cross-check is `cfg.remoteToken == t.srcToken`, which both satisfy. A single remote deposit can therefore be credited twice, on two different local assets, doubling that route's exposure while every per-token cap still reads as respected. Monitoring built around 'Executed with no matching Sent' would see two Executed events for one Sent and would need to know which registration was the legitimate one.

This is a governance-typo amplifier rather than an unprivileged attack — creating the second registration takes the owner multisig plus 48 h. What makes it worth fixing rather than documenting is that it is unrecoverable: registration is once-only and there is no `unregister`, so a mistyped route is permanent. The only remedy is `decreaseTokenLimits(token, 0, 0)`, which freezes the bad registration but also permanently strands anything already locked under it, since restoring caps is itself a 48 h timelocked action. The registry is the one part of this design where a mistake cannot be undone, which argues for the strictest possible validation at the point of entry.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack.t.sol::test_A6_TwoLocalTokensMayClaimTheSameRemoteAsset — PASSES.

1. Fixture already has usdx registered CANONICAL against (chain 1, REMOTE_WUSDX).
2. A second local token wdup is registered WRAPPED against the identical (chain 1, REMOTE_WUSDX) through the full 48 h timelock. No revert; `tokenConfig(wdup).kind == WRAPPED` asserted.
3. A signed transfer with `srcToken = REMOTE_WUSDX, dstToken = wdup` executes and mints 10e18 wdup to bob.
4. A signed transfer with `srcToken = REMOTE_WUSDX, dstToken = usdx` also executes and releases 10e18 usdx to bob. One remote asset, two live local claims, two independent cap budgets — asserted.

**Fix:** Add a reverse index and enforce it in `_register` at FerminuxBridge.sol:758:

```solidity
mapping(uint64 => mapping(address => address)) public localTokenFor; // remoteChainId => remoteToken => localToken
...
require(localTokenFor[remoteChainId][remoteToken] == address(0), "BRIDGE: remote asset already routed");
localTokenFor[remoteChainId][remoteToken] = localToken;
```

This is one storage write on a path that runs at most a handful of times per chain, and it makes the registry a bijection, which is what every other part of the contract already assumes. It also gives relayers and the UI a supported way to resolve a route in the reverse direction, which today requires scanning `registeredTokens`. Consider also requiring `remoteToken != address(0)` for a WRAPPED registration unless the remote asset really is that chain's native coin, since address(0) is the zero-value default and a forgotten argument currently registers silently.

### [LOW] One griefer holding both volume buckets shuts a whole route down for roughly 0.2% of the daily cap per day

**Detail:** FerminuxBridge.sol:565-571. `_consume` is called on the outbound bucket from `send()` (line 434) and on the inbound bucket from `execute()` (line 503), and both are permissionless. Neither is per-sender, so bucket capacity is a shared, first-come resource with no fairness mechanism.

docs/security-model.md §8 acknowledges the vector — 'Cap griefing | an attacker fills a token's inbound or outbound 24 h bucket with their own transfers, blocking everyone else | costs them only fees and gas. Cheap to do' — but treats it as one direction at a time and does not price it. Both buckets can be held simultaneously by a single actor with a single pot of capital, because the round trip that fills the outbound bucket on chain A is exactly what fills the inbound bucket on chain A when the same value comes home. The route is then closed in both directions for everyone else.

The cost is two fee legs per cycle at `feeBps`, so at the default 10 bps that is 0.2% of one dailyCap per day, plus gas, with capital equal to one dailyCap tied up and fully recoverable. Against the recommended week-1 posture in docs/operations.md §5 — dailyCap 25,000 FMX at the $0.53 reference, about $13,250 — that is roughly $26 per day to make the FMX route unusable, against a bridge whose day-one exposure budget is quoted at ~$53k. The economics are lopsided enough to belong in the launch numbers rather than in a footnote, particularly since the recommended caps deliberately start small and the griefing cost scales with the cap, so the route is cheapest to attack exactly when it is newest.

Worth noting what is NOT broken here: the window arithmetic itself held up. I measured true 24 h throughput from a cold bucket at 200.0% of dailyCap with 7-second top-ups (test_A4), matching the doc's claimed 2x exactly, and confirmed inbound and outbound are genuinely independent (test_A4b). Timestamp manipulation is not a lever either — 15 s of skew, the most a geth miner can push ahead, moves the bucket by 0.017% (test_B7).

**Exploit:** PoCs <scratch>/bridge-attack/test/Attack3.t.sol::test_C2_OneGrieferShutsTheWholeRouteAndWePriceIt and test/Attack2.t.sol::test_B3_AttackerFillsInboundBucketAndStallsEveryoneElse — both PASS.

C2, with dailyCap 500e18 and maxPerTransfer 100e18:
1. The griefer makes 5 sends of 100e18 each; outbound usage is asserted at the full 500e18.
2. The same capital comes home as 5 signed inbound transfers; inbound usage is asserted at the cap.
3. alice's 1e18 send reverts `BRIDGE: over 24h cap` — asserted.
4. A victim's fully signed 1e18 inbound transfer also reverts `BRIDGE: over 24h cap` — asserted. The route is dead in both directions.
5. Logged cost for the full-day lockout: 0.5e18 in fees against 500e18 of capital, i.e. 0.1% per leg, 0.2% per cycle, capital fully recoverable.

B3 shows the wrapped-route variant needs no collateral at all: five inbound executes fill the bucket, then the victim's signed transfer reverts.

**Fix:** There is no clean on-chain fix that does not create a worse problem — per-sender buckets are sybil-farmable and a priority queue is not something to invent in a bridge. Treat it as an operating parameter and a monitoring signal rather than a code change:

1. Put the number in docs/operations.md §5 next to the cap table: 'cost to deny this route for a day = 2 x feeBps x dailyCap', computed per phase, so cap sizing weighs DoS cost alongside the reorg inequality and the 2x loss budget.
2. Add a monitoring rule to §6: alert when either bucket exceeds ~80% of cap AND the top counterparty by volume accounts for more than half of it. That is the signature, and it is a cheap query over Sent/Executed.
3. Give operators a documented response. `pauseToken` plus a manual allowlist is not available in this design, so the realistic lever is raising `feeBps` toward `MAX_FEE_BPS` for that route, which multiplies the griefer's cost tenfold — note this is `setFeeBps`, is global rather than per-token, and is timelocked 48 h, so it is a deterrent to pre-position rather than an incident response.
4. If per-token fees are ever added, make the griefing cost per-route tunable, which is the only structural improvement available here.

### [LOW] _verifySignatures' arity guard rejects a bundle that contains a full valid quorum, purely because it also contains one stale signature

**Detail:** FerminuxBridge.sol:529, `require(n <= validators.length, "BRIDGE: too many signatures")`. The intent is a gas bound on the O(n^2) duplicate scan, and with duplicates already rejected at line 537 a bundle can never usefully exceed the validator count. But the check runs on raw array length before any signature is recovered, so it fails bundles whose CONTENT is perfectly valid.

The collision is with validator rotation. Relayers reasonably collect signatures from every validator that responds rather than exactly `threshold` of them — it is the obvious way to be robust to one validator being slow. With a 3-validator set at threshold 2, a 3-signature bundle is normal practice. The moment `removeValidator` executes, `validators.length` drops to 2 and every such in-flight bundle becomes unexecutable on arity, even though two current, valid, distinct validators signed it and the threshold is met. The relayer must know to re-slice the array; a naive relayer or a user submitting published signatures by hand simply sees `BRIDGE: too many signatures` and has no way to interpret it.

docs/security-model.md §6 covers the adjacent case — 'Validator rotation invalidates in-flight signatures... Rotating with transfers in flight strands them until they are re-signed. Drain the queue before rotating' — and cites test_Sig_RemovedValidatorNoLongerCounts and test_Sig_RaisedThresholdInvalidatesOldQuorum. Both of those are about signatures that genuinely no longer count. This case is different and is not covered: the signatures still count, the quorum is present, and the transfer is rejected anyway. It is recoverable by re-submitting a trimmed array, so the impact is confined to relayer fragility during a rotation — but a rotation is exactly when the operator is already under stress, and `removeValidator` is the documented response to a validator compromise.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack2.t.sol::test_B6_StaleSignatureInABundleInvalidatesAValidQuorum — PASSES.

1. Threshold 2 of 3. A relayer collects all three validator signatures over the same transfer — standard belt-and-braces.
2. v3 is rotated out via the full 48 h `removeValidator` timelock. v1 and v2 remain valid validators and both signed.
3. `bridge.execute(t, three)` reverts `BRIDGE: too many signatures` — asserted. Not `not a validator`, not `below threshold`: the bundle is rejected on array length before a single `ecrecover` runs.
4. `bridge.execute(t, _sigs(k1, k2, t))` with the identical transfer succeeds and mints 10e18 to bob — asserted. Nothing about the transfer or the signatures changed; only the array length did.

**Fix:** Keep the gas bound but decouple it from the live validator count, so rotation cannot invalidate a bundle whose content is valid. Replace line 529 with a constant ceiling:

```solidity
require(n <= MAX_VALIDATORS, "BRIDGE: too many signatures");
```

32 recoveries plus a 496-comparison scan is roughly 100k gas — a real bound, permanently stable, and independent of governance. Signatures from removed validators are still rejected one at a time by `require(isValidator[signer])` at line 535, which is the correct place for that decision.

If the stricter arity is wanted, the alternative is to skip non-validator signatures instead of reverting on them and count only distinct current validators against the threshold — but that is a larger behavioural change and weakens the useful property that a bundle containing a bad signature is loudly rejected, so the constant ceiling is the better trade. Add a regression test asserting that a bundle of N signatures still executes after the set shrinks below N, as long as a current quorum is present.

### [LOW] A matured timelock action can be held for the 14-day grace period and fired with no fresh on-chain warning

**Detail:** FerminuxBridge.sol:690-709. `executeAction` requires `block.timestamp >= a.eta` and `block.timestamp <= a.eta + GRACE_PERIOD`, with `GRACE_PERIOD = 14 days` (line 115). Between those two instants the action is a loaded gun the owner can fire in any block, and firing it emits `ActionExecuted` only as it lands — there is no second announcement.

The timelock's security value is stated in docs/security-model.md §1 as 'The timelock does not remove that power; it makes the power observable before it is used', and §4 puts the operational weight on the queue-time alert: 'every queued action emits ActionQueued(actionId, selector, data, eta) 48 hours before it can fire — monitor it, because it is the single highest-value alert in the system' and 'users who see a hostile ActionQueued have 48 hours to bridge out, if they are watching.' That 48 hours is measured from queue time, not from execution time. A patient owner queues a hostile action during a quiet period, lets the 48 h alert age out of everyone's attention, and then executes up to 14 days later at a moment of their choosing — during a market event, or immediately after `pause()` has already trapped everyone. The grace period is described in §4 purely as a staleness protection ('a queued action goes stale GRACE_PERIOD = 14 days after its eta'), which is its intent, but the same window is what makes the delayed-trigger pattern possible.

This is inherent to how most timelocks work and is not a bug. It is worth recording because the docs lean unusually hard on the announcement as the primary control, and because the specific combination that matters — `pause()` first, then fire a matured `setThreshold(1)` while nobody can exit — is not called out in the incident-response material.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack.t.sol::test_A9_MaturedActionCanBeHeldAndFiredInstantly — PASSES.

1. The owner queues `setThreshold(1)`. `ActionQueued` fires once, here.
2. `vm.warp(+48 hours)` — the action matures. No event.
3. `vm.warp(+13 days)` — the action stays live and silent for the whole grace period. Watchers have seen nothing since step 1.
4. `bridge.executeAction(id)` succeeds; `threshold() == 1` asserted. The quorum has been halved with no fresh on-chain notice.
5. Demonstrating the consequence: a transfer signed by a SINGLE validator now executes, minting 100e18 to the attacker — asserted. A single compromised key is now sufficient.

Separately confirmed as working defences (test_D_ExecuteActionCannotRunEarlyTwiceOrAfterCancel): early execution reverts `BRIDGE: timelock not elapsed`, double execution reverts `BRIDGE: action executed`, post-cancel execution reverts `BRIDGE: action canceled`, and stored calldata cannot be made to dispatch to an unannounced selector (test_B5).

**Fix:** Cheapest fix is monitoring, not code: add `ActionExecuted` and `ActionCanceled` to the alert list in docs/operations.md §6 alongside `ActionQueued`, and add a standing check for 'matured but unexecuted actions' — `getAction(i)` for every `i < actionCount()` where `!executed && !canceled && block.timestamp >= eta` — so a loaded action is visible for as long as it is loaded rather than only at the two instants it moves. That is a few lines in the monitoring script and it removes the quiet period entirely.

If a code change is wanted, shorten `GRACE_PERIOD` from 14 days to something closer to a normal operational window (48-72 h), so a matured action must be executed while the queue-time alert is still fresh or be re-queued with a new 48 h announcement. Also consider re-checking the pause state at execution time for the enlarging selectors — refusing `addValidator`, `setThreshold` and `setTokenLimits` while `paused` is true would close the specific pause-then-fire sequence, at the cost of making recovery-by-governance require an unpause first.

### [INFO] feeCollector may be set to the bridge itself, silently reclassifying accrued fees as rescue()-able surplus

**Detail:** FerminuxBridge.sol:833-837, `setFeeCollector` requires only `newCollector != address(0)`. Setting it to `address(this)` is permitted. `withdrawFees` (line 576) then zeroes `accruedFees[token]` and performs a self-transfer — for ERC20 a real no-op transfer that succeeds, for native a call into `receive()` that succeeds — so the balance does not move but the reservation disappears. `surplusOf()` (line 386) subtracts `accruedFees`, so the entire fee balance becomes surplus and is immediately withdrawable by `rescue()`.

No privilege is gained: `setFeeCollector` is one of the nine timelocked `onlySelf` selectors, so it takes the owner multisig plus 48 h, and `rescue` is `onlyOwner` — an owner who can do this could simply set the collector to their own address and call `withdrawFees` directly, in one step instead of three. So this is not an escalation path.

It is worth recording for two reasons. First, it is a third route by which value crosses from a reserved bucket into the unreserved one, alongside the recipient-is-the-bridge finding, and the contract's accounting story rests on those buckets being one-way. Second, it defeats a stated property: docs/security-model.md §4 notes that `withdrawFees` sends 'fees only — but note setFeeCollector is timelocked, so the destination is the current collector', which is offered as a constraint on where fees can go. If the current collector is the bridge, the destination becomes 'wherever the owner sends it next, instantly, via rescue' — the 48 h notice on the collector change no longer constrains the eventual destination.

**Exploit:** PoC <scratch>/bridge-attack/test/Attack3.t.sol::test_C3_FeeCollectorMayBeTheBridgeItself — PASSES.

1. alice sends 100 USDX; `accruedFees(usdx)` is 0.1e18 and `surplusOf(usdx)` is 0.
2. `setFeeCollector(address(bridge))` is queued and executed through the full 48 h timelock — no revert.
3. `vm.prank(owner); bridge.withdrawFees(usdx)` performs the self-transfer and succeeds.
4. Asserted: `accruedFees(usdx) == 0` and `surplusOf(usdx) == 0.1e18`. The token balance never moved; the fees are now unreserved and `rescue()` will pay them out to any address in a single instant transaction.

**Fix:** One line in `setFeeCollector` at FerminuxBridge.sol:834:

```solidity
require(newCollector != address(0) && newCollector != address(this), "BRIDGE: bad collector");
```
